# Documentation

เอกสารทั้งหมดของโปรเจกต์นี้อยู่ที่นี่ที่เดียว งานทุกชิ้นที่แตะโค้ดต้องผ่านสองขั้นตอน:
**ออกแบบก่อน แล้วค่อยลงมือ** และ **บันทึกสิ่งที่เปลี่ยนหลังทำเสร็จ**

## โครงสร้าง

```text
docs/
  design/      แผน/ดีไซน์ ที่เขียน "ก่อน" เริ่มเขียนโค้ด
  changes/     บันทึกสิ่งที่เปลี่ยนจริง เขียน "หลัง" ทำเสร็จ
  templates/   เทมเพลตของทั้งสองแบบ
```

## กติกา

1. **Design first.** ก่อนแตะโค้ดสำหรับงานที่ไม่ใช่ของจิ๊บจ๊อย ให้เขียน design doc
   ลง `docs/design/` โดยคัดลอกจาก [templates/design-doc.md](templates/design-doc.md)
   ตั้งชื่อไฟล์เป็น `YYYY-MM-DD-<slug>.md`
2. **รอความเห็นชอบ.** ถ้ามีทางเลือกที่ผลลัพธ์ต่างกันอย่างมีนัยสำคัญ ให้ถามก่อน
   อย่าเดาแล้วลงมือ
3. **Record after.** เมื่องานเสร็จ เขียนบันทึกลง `docs/changes/` โดยคัดลอกจาก
   [templates/change-record.md](templates/change-record.md) ตั้งชื่อไฟล์แบบเดียวกัน
   และลิงก์กลับไปหา design doc ที่เกี่ยวข้อง
4. **หนึ่งงาน หนึ่งคู่เอกสาร.** design doc กับ change record ควรจับคู่กันได้
   ถ้างานเล็กจนไม่ต้องมี design doc ก็ยังต้องมี change record เสมอ
5. **เขียนให้สั้นและตรง.** เอกสารมีไว้ให้คนที่มาทีหลังเข้าใจ *ทำไม* ไม่ใช่ *อะไร*
   — ส่วน *อะไร* อ่านจาก diff ได้อยู่แล้ว

## เมื่อไหร่ต้องมี design doc

ต้องมี เมื่องานนั้น:

- เพิ่ม/แก้ route, page, หรือ API contract
- แก้ schema ฐานข้อมูล หรือเพิ่ม migration
- แตะ observability (tracing, metrics, logging)
- แก้ `Dockerfile`, CI, หรือสมมติฐานของ runtime
- เพิ่ม dependency ใหม่ หรือเปลี่ยนโครงสร้างโฟลเดอร์

ไม่ต้องมี เมื่อเป็น: แก้ typo, ปรับ copy เล็กน้อย, จัด format, bump เวอร์ชัน patch
— กรณีเหล่านี้เขียนแค่ change record พอ
