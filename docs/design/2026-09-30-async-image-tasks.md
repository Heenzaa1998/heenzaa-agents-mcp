# งานภาพแบบ async: ไม่ทิ้งภาพที่รอเกินเวลา

- **วันที่:** 2026-09-30
- **สถานะ:** approved
- **Change record:** `docs/changes/2026-09-30-async-image-tasks.md` (เติมเมื่อทำเสร็จ)

## ปัญหา

`generate_image` / `edit_image` สร้างงานที่ KIE แล้วรอผลไม่เกิน 240 วินาที ถ้าเกิน ระบบโยน error
และบันทึกประวัติเป็น `fail` โดย**ไม่มี taskId** ทั้งที่ KIE ยังทำงานต่อจนเสร็จและหักเครดิต
เมื่อ 2026-09-28 สั่งภาพ 11 ช็อตพร้อมกัน หมดเวลา 4 ช็อต เสีย 24 เครดิตโดยไม่ได้ภาพ และหน้า
`/projects` แสดงค่าใช้จ่ายต่ำกว่าจริง

## ขอบเขต

**อยู่ในขอบเขต:**
- บันทึกประวัติเป็น `pending` พร้อม taskId **ทันทีที่ KIE รับงาน** (เหมือนวิดีโอ) แล้วค่อยปิดเป็น
  `success`/`fail` เมื่อรู้ผล
- เมื่อรอครบเวลาแล้วยังไม่เสร็จ ไม่โยน error แต่ตอบกลับ `pending` + `task_id` ประวัติคง `pending`
- `get_task_status` ใช้ตามผลภาพได้ (โค้ดเดิมรองรับอยู่แล้ว: เก็บไฟล์ใต้ `images/`, ทำ thumbnail,
  ปิดประวัติพร้อมเครดิต) ปรับคำอธิบาย tool ให้ครอบคลุมภาพ
- gallery แสดงภาพที่ `pending` พร้อมปุ่มตรวจสถานะ (ใช้ของวิดีโอที่มีอยู่)

**ไม่อยู่ในขอบเขต:**
- callback/webhook จาก KIE (ต้องมี endpoint สาธารณะเพิ่ม ยังไม่จำเป็น)
- ให้ผู้เรียกเลือกเวลารอเอง

## ทางเลือกที่พิจารณา

| ทางเลือก | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| A: ตอบ pending เมื่อหมดเวลา + บันทึก taskId ตั้งแต่เริ่ม | โค้ดน้อย ใช้ `get_task_status` เดิม ไม่เสียเครดิตฟรี | ผู้เรียกต้องตามผลเองในกรณีหมดเวลา (เหมือนวิดีโอ) |
| B: ภาพเป็น async ทั้งหมดเหมือนวิดีโอ | ไม่มี request ค้างนาน | ภาพส่วนใหญ่เสร็จใน 1–2 นาที ต้องเรียก 2 รอบทุกครั้ง ใช้งานลำบากขึ้น |
| C: webhook จาก KIE | ไม่ต้อง poll | ต้องมี endpoint สาธารณะ + ตรวจลายเซ็น งานใหญ่กว่าปัญหา |

## ทางที่เลือก

**A** — ภาพที่เสร็จทันยังได้ผลในรอบเดียวเหมือนเดิม เฉพาะกรณีหมดเวลาที่เปลี่ยนจาก "เสียของ" เป็น
"ตามได้ทีหลัง"

- client รับ hook `onStarted(taskId)` ให้ service บันทึกแถว `pending` ก่อนเริ่มรอ
- ผลจาก client เป็น `{ taskId, state: "success", urls, creditsConsumed }` หรือ `{ taskId, state: "pending" }`
- งานที่ KIE ตอบ `fail` ระหว่างรอ → ปิดประวัติเป็น `fail` พร้อมเหตุผล แล้วโยน error เหมือนเดิม
- `ImageGenerationResult` เพิ่ม `pending: boolean`; MCP ตอบข้อความบอก task_id เมื่อ pending

## ความเสี่ยง

- `get_task_status` ที่เรียกซ้ำกับงานสำเร็จแล้ว จะเก็บไฟล์ทับ key เดิม (ไม่เพิ่มไฟล์) และปิดประวัติซ้ำ
  ด้วยค่าเดิม ไม่มีผลข้างเคียง
- แถว `pending` ที่ไม่มีใครตาม จะค้างใน gallery จนกด "ตรวจสถานะ" ยอมรับได้ (เหมือนวิดีโอ)

## การทดสอบ

- unit: service บันทึก pending ก่อนรอ, ปิด success พร้อมเครดิต, ปิด fail เมื่อ KIE ตอบ fail,
  คง pending และคืน `pending: true` เมื่อหมดเวลา
- production: เรียก `get_task_status` ด้วย taskId ของภาพที่สำเร็จแล้ว ต้องได้ลิงก์ภาพกลับ (ไม่ใช้เครดิต)
